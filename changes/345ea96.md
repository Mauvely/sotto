# 345ea96 — One apt at a time, and the lock timeout was not enough

## Bug Fixes

- **Concurrent `apt-get update` corrupted the package cache.**

  ```
  E: Problem renaming the file /var/cache/apt/pkgcache.bin.mrWAip to
     /var/cache/apt/pkgcache.bin - rename (2: No such file or directory)
  E: The package cache file is corrupted
  ```

  The previous fix added `-o DPkg::Lock::Timeout=600`, which makes apt wait for
  the **dpkg** lock. `apt-get update` does not contend on that lock; it rebuilds
  `/var/cache/apt/pkgcache.bin`. So the first fix removed one race and left this
  one, on a machine where seven runner services can start apt in the same second.

## Changes

- Every `apt-get` in `ci.yml` and `release.yml` now runs under
  `flock -w 900 /var/lock/mauvely-apt.lock`, which covers `update` as well as
  `install`.
- `-o DPkg::Lock::Timeout=600` is kept rather than replaced. The two do different
  jobs: flock serialises these workflows against each other, the option waits for
  anything else on the box that holds dpkg.

## Verification

All 17 workflows across the eight repositories re-parse as valid YAML, every

step is present in all eight.
